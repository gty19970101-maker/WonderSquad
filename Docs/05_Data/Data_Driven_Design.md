# Data-Driven Design

## 系统目标

定义 Wonder Squad 的数据驱动规则，使角色能力、机关、道具、配方、状态效果、关卡目标和触发器可配置、可校验、可版本化，并为未来玩家关卡编辑器保留安全扩展点。

数据驱动用于减少硬编码和提高内容生产效率，不用于提前建设通用脚本平台。

## 系统边界

负责：

- 静态定义、运行时状态和表现状态的分离。
- 稳定 ID、格式版本、引用和校验。
- 允许的数据类型和扩展流程。
- Trigger、Condition、Action 白名单。
- 多解法与关卡变体的数据形状。
- 未来不可信玩家内容的安全边界。

不负责：

- 完整业务运行逻辑。
- Unity 玩家关卡编辑器 UI。
- 在线内容包、审核和发布。
- 任意 C# 类型、方法或脚本执行。
- 远程热更新。
- 构建大型通用内容平台。

## 核心流程

### 内容制作

```text
创建设计定义
→ 分配稳定 ID 与 SchemaVersion
→ 配置引用和白名单类型
→ 编辑器/构建前校验
→ 加载到测试场景
→ 运行时实例化权威状态
→ 表现层订阅状态
```

### 内容更新

```text
修改定义
→ 保持稳定 ID
→ 必要时提升 SchemaVersion
→ 执行迁移或兼容规则
→ 重新校验所有引用
→ 回归联机和关卡测试
```

### 未来玩家内容

```text
编辑器输出受限内容包
→ 校验格式/大小/依赖/白名单
→ 作者通关验证
→ 上传与审核
→ 下载到隔离内容目录
→ 使用相同运行时读取
```

最后一条流程不属于 MVP，只定义兼容方向。

## 主要状态

### 内容生命周期

- `Draft`
- `Validating`
- `Valid`
- `Invalid`
- `Loaded`
- `Deprecated`

### 三层数据

1. **静态定义**
   - RoleDefinition
   - AbilityDefinition
   - ItemDefinition
   - RecipeDefinition
   - StatusDefinition
   - PuzzleDefinition
   - LevelDefinition
   - LevelVariantDefinition

2. **主机权威运行时状态**
   - 玩家与角色
   - 能力状态
   - 库存和道具实例
   - 机关和触发器状态
   - 临时状态与救援
   - 关卡种子与变体

3. **客户端表现状态**
   - UI 布局
   - 动画、粒子和音效
   - 标记屏幕位置
   - 摄像机

静态定义不可在会话中被客户端修改为权威结果。

## 与其他系统的依赖

本规范是上游约束，不对应一个反向依赖所有系统的运行时程序集。

- `Core/Contracts` 定义稳定 ID、版本和内容端口。
- `Content/Validation` 依赖 Core 与 Unity 资产序列化。
- Ability、Item、Crafting、Puzzle、Status 和 Level 只读消费各自定义。
- Network 只传输稳定 ID 和运行时状态。
- Save 使用独立设置 SchemaVersion，不依赖关卡内容实现。

本规范依赖 Unity 资产序列化或等价的数据加载机制，但不要求所有定义都使用同一种物理文件格式。

## 联机同步要求

- 客户端与主机必须使用兼容内容版本。
- 网络传输稳定 ID、运行时实例 ID 和必要状态，不传输整个 ScriptableObject。
- MVP 同步固定默认变体；随机种子选择保留为后续扩展。
- 客户端不能通过修改本地定义改变主机判定。
- 内容版本不兼容时阻止加入或使用安全回退。
- 触发器和动作只在主机权威运行时改变共享状态。
- 未来玩家内容必须被视为不可信输入。

## MVP范围

### 必须数据驱动

- 角色与能力。
- 能力标签。
- 道具和物品标签。
- 配方与材料。
- 临时状态与救援参数。
- 三个机关的状态、触发器、条件、动作和解法路径。
- 《沉睡森林》的目标、检查点和恢复点。
- 《沉睡森林》的小地图世界边界和背景资源 ID。
- 关卡内变体候选。
- 固定默认 LevelVariant。
- 快捷意图与标记语义键。

### MVP 白名单

Trigger：

- 交互
- 能力作用
- 物品放置
- 区域进入
- 计时
- 人数满足

Condition：

- 能力标签
- 物品标签
- 库存数量
- 最小参与人数
- 机关状态
- 临时状态

Action：

- 设置机关状态
- 消耗库存
- 生成物品
- 开启路线
- 施加/解除状态
- 激活检查点
- 完成目标
- 局部重置

## 非MVP范围

- 玩家关卡编辑器。
- 通用可视化脚本图。
- 任意代码、反射方法和动态程序集。
- UGC 在线内容包。
- 自动审核。
- 热更新玩法逻辑。
- 无限嵌套条件。
- 全项目通用数据平台。

## 验收标准

- 所有定义有稳定、唯一 ID。
- 必要定义有 SchemaVersion。
- 缺失引用、重复 ID 和不支持类型能在进入关卡前发现。
- 关卡和机关不通过对象名称查找关键依赖。
- 机关不直接判断具体角色类名，只查询能力标签。
- 每个主线问题至少有角色优势、通用替代和恢复路径数据。
- 验证器能发现依赖单一角色且无替代的主线路径。
- 验证器只检查声明路径、引用、白名单和资源预算，不证明物理或时序上必然可通关。
- 四角色可重复选择的 65 个无序 2～4 人组合均通过声明路径结构校验。
- 固定默认关卡变体可被所有客户端解析。
- 运行时状态和静态定义分离。
- 新增一种数据类型时必须同时增加验证和测试。

## 风险与待确认事项

### 风险

- 把数据驱动误解为“所有逻辑都配置化”。
- 白名单类型过多，形成自制脚本语言。
- ScriptableObject 引用在重命名或移动时失效。
- 未来 UGC 需求促使 MVP 提前实现内容平台。
- 可通关性验证只能做结构检查，无法替代真实游玩。

### 待确认

- 稳定 ID 使用人工可读字符串、GUID 还是二者映射；建议内容 ID 可读、资产 GUID 只作内部引用。
- 配置采用 ScriptableObject、JSON 还是混合方案；MVP 建议内置内容优先 ScriptableObject。
- SchemaVersion 的迁移工具何时开始实现。
- 自动可通关性校验只做结构约束；实际可通关性固定由自动化流程测试和人工代表性矩阵验证。
- 未来玩家内容是否允许自带美术资源；当前不做决定。
