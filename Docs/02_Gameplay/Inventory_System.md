# Inventory System

## 系统目标

为资源收集和制作提供简单、低摩擦、主机权威的库存能力，避免个人争抢和复杂背包管理干扰合作解谜。

MVP 普通资源优先使用团队共享库存，大型或关键道具保留为场景实体。

## 系统边界

负责：

- 资源数量查询、堆叠和容量规则。
- 增加、预留、取消预留和原子消耗。
- 团队共享库存状态。
- 能力造成的有限成本修饰后的最终材料事务。
- 库存变更事件。

不负责：

- 世界物品的位置、持有和物理。
- 配方判定与输出生成。
- 装备、快捷栏、耐久和重量。
- 长期账号库存。
- 客户端本地修改权威数量。

## 核心流程

### 获得资源

```text
采集或回收结果由主机确认
→ 查询物品定义与堆叠规则
→ 尝试加入团队库存
→ 写入新数量
→ 同步变更
→ UI 更新
```

### 制作消耗

```text
Crafting 提交材料清单
→ 应用主机确认的能力修饰
→ 一次检查全部材料
→ 预留
→ 制作成功时一次扣除
→ 制作失败时释放预留
```

任何制作都不得出现只扣除部分材料后失败的状态。

## 主要状态

### 物品条目

- `AvailableQuantity`
- `ReservedQuantity`
- `TotalQuantity`

### 事务

- `Pending`
- `Reserved`
- `Committed`
- `Cancelled`
- `Rejected`

MVP 可使用同步方法完成原子事务，但业务语义必须保持上述边界。

## 与其他系统的依赖

编译时依赖：

- `Core/Contracts`：ItemDefinitionId、库存命令、查询和事件。
- `Content`：资源分类、堆叠和容量定义。

通过端口或事件协作：

- Crafting 与 Puzzle 通过 `IInventoryQuery` 和 `IInventoryCommandPort` 工作。
- Ability 的成本修饰通过不可变 `CostModifier` 输入，不反向引用 Ability。
- Communication 和 UI 消费 InventoryChanged 或资源不足原因。
- Network Adapter 复制权威快照。

Inventory 不依赖运行时 Item、Crafting、Puzzle、Communication 或 Ability 实现。

## 联机同步要求

- 主机是库存唯一写入者。
- 客户端只接收快照或增量并用于显示。
- 增加与消耗请求包含 RequestId。
- 同一采集结果只能加入一次。
- 能力修饰由主机根据请求时角色状态计算。
- 迟加入者获得当前完整团队库存。
- 玩家离开不带走团队资源。

## MVP范围

- 团队共享资源库存。
- 至少三类资源。
- 数量查询、增加、预留和原子消耗。
- 制作与机关条件。
- 资源不足原因。
- 简洁 UI 摘要。

## 非MVP范围

- 个人背包网格。
- 装备栏、仓库和交易。
- 重量、耐久、品质和稀有度。
- 长期资源存档。
- 掉落分配和需求/贪婪。
- 复杂反作弊经济审计。

## 验收标准

- 两名玩家同时采集或制作不会产生重复数量。
- 制作材料要么全部扣除，要么完全不扣。
- 迟加入客户端看到正确库存。
- 玩家离开不破坏团队库存。
- 能力修饰不会使数量变成负数或绕过材料要求。
- 大型关键道具不会被错误表示为抽象数量。
- UI 不拥有库存写入能力。

## 风险与待确认事项

### 风险

- 团队库存削弱实物搬运的合作感。
- 预留事务复杂度超过 MVP 需要。
- 能力成本修饰与配方显示不一致。
- 资源回收造成无限复制。

### 待确认

- MVP 之后是否增加团队库存容量；第一阶段不设容量上限。
- MVP 之后是否展示个人采集贡献；第一阶段只显示团队总量，不做个人排行。

已确认：

- Resource 拾取后直接进入团队库存。
- Tool 与 PuzzlePart 保持场景实例，不进入团队库存。
