# Crafting System

## 系统目标

把团队收集的资源转化为可以改变环境、开启路线或推进机关的工具，为角色能力之外提供通用替代解法。

制作应简单、可理解并直接服务关卡，不形成复杂生产或养成系统。

## 系统边界

负责：

- RecipeDefinition、材料、工作点和输出。
- 配方可用性与失败原因。
- 主机权威的材料修饰、预留、原子消耗和输出生成。
- 角色能力带来的低成本或替代材料优势。
- 通用配方确保无特定角色仍能通关。
- 记录采用的配方和关联解法。

不负责：

- 资源采集。
- 团队库存底层事务。
- 场景道具物理生命周期。
- 机关完成。
- 复杂制作队列和长期技能。

## 核心流程

```text
玩家接近制作点
→ 查询可用配方
→ 选择配方
→ 客户端显示预计材料和能力修饰
→ 提交 CraftRequest
→ 主机重新计算最终成本
→ 校验工作点与材料
→ 原子预留/消耗
→ 生成库存输出或场景道具
→ 同步结果与反馈
```

失败时：

- 材料不足：不扣除，显示缺少项。
- 工作点无效：不扣除。
- 请求重复：返回既有结果。
- 输出生成失败：回滚材料或使用预定义安全恢复。

## 主要状态

- `Unavailable`
- `Available`
- `Requested`
- `MaterialsReserved`
- `Producing`
- `Succeeded`
- `Rejected`
- `RolledBack`

MVP 制作可以即时完成，但仍需保留事务状态边界。

## 与其他系统的依赖

编译时依赖：

- `Core/Contracts`：CraftRequest、库存端口、物品生成端口和 CraftResult。
- `Content`：RecipeDefinition。

通过端口或事件协作：

- 使用 `IInventoryQuery` 与 `IInventoryCommandPort` 完成材料事务。
- 使用 `IItemSpawnPort` 生成场景输出。
- 接收不可变 CostModifier，不引用 Ability 实现。
- 发布 CraftSucceeded/CraftRejected，供 Puzzle、Communication 和 UI 消费。
- Network Adapter 传输请求与结果。

Crafting 不依赖 Inventory、Item、Ability、Interaction、Puzzle 或 Communication 的实现程序集。

## 联机同步要求

- 主机计算最终材料成本。
- 客户端显示值仅作预览。
- 每个 CraftRequest 有 RequestId。
- 相同请求不能重复扣除或重复生成。
- 输出由主机创建并同步。
- 团队同时发起制作时按主机处理顺序执行。
- 能力修饰使用请求处理时的权威角色状态。

## MVP范围

- 少量服务《沉睡森林》的配方。
- 至少两种有效制作。
- 团队共享材料。
- 工匠或相关能力的成本优势。
- 缺少该能力时的通用配方。
- 制作工作点。
- 明确失败原因。
- Resource 只作为材料数量；Tool 输出为场景实例并放入预定义生成点或 Socket。

## 非MVP范围

- 制作等级、品质和随机结果。
- 长制作队列。
- 工作台升级。
- 蓝图掉落和复杂配方树。
- 自动化生产。
- 玩家自定义配方。
- 长期经济平衡。

## 验收标准

- 配方可通过数据调整，不修改业务流程。
- 材料要么全部扣除，要么完全不扣。
- 角色优势降低成本或步骤，但不形成必选。
- 无工匠代表阵容仍能制作主线所需工具。
- 重复、并发和输出失败不会复制资源。
- 制作结果能实际改变环境或推进机关。
- UI 预览与主机结果不一致时提供清晰反馈。

## 风险与待确认事项

### 风险

- 配方过多削弱解谜节奏。
- 能力修饰导致 UI 和权威成本不一致。
- 通用配方成本过高，形成变相角色锁。
- 即时制作缺少合作感。

### 待确认

- 《沉睡森林》的最终配方清单。
- 是否需要两人共同操作制作点。
- 《沉睡森林》各配方输出对应的预定义生成点或 Socket。
- 工匠优势具体采用减少材料、缩短步骤还是两者之一。
