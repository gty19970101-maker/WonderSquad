# Character Ability System

## 系统目标

让不同角色通过能力改变探索和解谜方式，产生分工、互补和重玩价值，同时确保缺少任何特定角色时仍有合理通用解法。

系统优先采用数据驱动的角色、能力和能力标签定义。

## 系统边界

负责：

- 角色与能力的静态定义。
- 角色拥有能力的关系。
- 能力标签、输入、目标条件、持续时间和轻量冷却。
- 主机权威的能力合法性校验。
- 将能力结果转为标准环境输入或修饰。
- 为 UI、机关、道具和制作提供能力查询。

不负责：

- 具体关卡是否完成。
- 在能力系统中硬编码某个机关。
- 复杂技能树、伤害、法力、等级和装备加成。
- 保证关卡替代路径；该责任由关卡与机关设计共同承担。

## 核心流程

```text
玩家选择角色
→ 加载 RoleDefinition
→ 获得 AbilityDefinition 列表
→ 玩家对目标发起能力请求
→ 主机校验角色、能力、距离、目标标签与当前状态
→ 接受或拒绝
→ 接受时执行标准化效果
→ 同步持续状态与表现事件
```

环境对象只声明可接受的能力标签，例如：

- `Traversal.HighReach`
- `Crafting.Efficient`
- `Magic.EnvironmentShift`
- `Observation.Reveal`

对象不得判断“玩家是否为魔法师”。

MVP 能力表现受以下实现约束：

- 探险家只使用关卡配置的 Anchor。
- 工匠只对配置的 Socket 进行修复或放置。
- 魔法师只切换预定义 EnvironmentState。
- 观察者只揭示预定义 RevealTarget。
- 不做自由绳索、任意建造、连续环境变形或复杂网络物理。

## 主要状态

### 能力生命周期

- `Unavailable`
- `Ready`
- `Activating`
- `Active`
- `Cooldown`
- `BlockedByStatus`

并非所有能力都需要完整生命周期。被动能力可只提供标签或修饰查询。

### MVP 角色方向

| 角色 | 能力方向 | 典型优势 |
|---|---|---|
| 探险家 | 跳跃、攀爬、绳索、快速运送 | 快速建立地形路线 |
| 工匠 | 制作、修复、临时结构 | 更少资源或更稳定工具 |
| 魔法师 | 激活魔法、改变环境、牵引 | 创造短时环境窗口 |
| 观察者 | 揭示、分析、团队标记增强 | 发现隐藏路线与信息 |

### MVP 标志性能力

| 角色 | AbilityId | MVP 行为 |
|---|---|---|
| 探险家 | `ability.explorer.anchor_route` | 在预定义 Anchor 间建立或使用快捷路线 |
| 工匠 | `ability.crafter.socket_repair` | 修复预定义 Socket，或为指定配方应用一次成本修饰 |
| 魔法师 | `ability.mage.environment_shift` | 在预定义 EnvironmentState 间切换 |
| 观察者 | `ability.observer.reveal` | 揭示预定义 RevealTarget 并共享给队伍 |

第一阶段不增加第二个主动能力。

## 与其他系统的依赖

编译时依赖：

- `Core/Contracts`：PlayerId、AbilityCommand、AbilityApplied、目标端口。
- `Content`：RoleDefinition、AbilityDefinition 和 AbilityTag。

通过端口或事件协作：

- 使用 `IPlayerQuery` 读取位置、角色与状态。
- 使用 `IAbilityTargetPort` 向环境提交标准化效果。
- 发布 AbilityApplied，供 Item、Crafting、Puzzle、Level 和表现层消费。
- Network Adapter 将远端输入映射为 AbilityCommand。

Ability 不直接引用 Player、Interaction、Item、Crafting、Puzzle、Status 或 Level 的实现程序集。

## 联机同步要求

- 角色选择由主机确认并同步。
- 客户端发送能力输入，不直接执行共享环境结果。
- 主机校验目标、距离、当前角色、能力和状态。
- 同步正在持续的能力状态、目标和权威结束时间。
- 短暂表现可使用事件；迟加入者需要看到的环境结果必须是持续状态。
- 能力请求包含 RequestId，避免重复执行。
- 客户端本地可以预播低风险动作，但必须接受拒绝或校正。

## MVP范围

- 探险家、工匠、魔法师和观察者四个初始角色。
- 每个角色一个服务《沉睡森林》的标志性能力。
- 允许重复选择角色。
- 数据驱动 RoleDefinition、AbilityDefinition 和 AbilityTag。
- 能力作用于移动机会、制作修饰、环境激活和线索揭示。
- 每种已实现能力在《沉睡森林》中至少一次明显价值。
- 至少一个核心问题因角色组合不同产生不同路径。
- 通用替代方案始终存在。

## 非MVP范围

- 大量角色。
- 技能树、等级、装备和数值成长。
- 战斗技能、伤害和敌对目标。
- 玩家自定义能力。
- 任意脚本式能力。
- 在线能力平衡后台。

## 验收标准

- 能力定义可以在不修改关卡代码的情况下调整标签和参数。
- 机关和道具不直接引用具体角色类名。
- 主机拒绝无权限、越距、错误目标和被状态阻断的能力请求。
- 每种能力对团队有可观察的价值。
- 缺少任一特定角色的代表阵容仍能完成《沉睡森林》。
- 当前四角色的任意 2～4 人组合都存在声明的主线通路。
- 通用替代解法不会退化为大量重复刷取。
- 能力结果在所有客户端一致。

## 风险与待确认事项

### 风险

- 能力标签过细，形成难以维护的隐式脚本语言。
- 工匠效率过高，使其他制作路径失去意义。
- 观察者的信息能力难以让其他玩家感知贡献。
- 魔法环境变化与网络物理冲突。
- 通用替代方案过强，削弱角色差异。

### 待确认

- 四个标志性能力的最终参数与动画表现。
- 重复角色在同一目标上的能力效果是否叠加；默认不叠加环境状态，只允许并行操作不同目标。
- 能力是否存在冷却，还是由场景机会限制。
- 各 Anchor、Socket、EnvironmentState 和 RevealTarget 的《沉睡森林》配置清单。
