# Wonder Squad MVP 开发计划 v1.1

## 1. 文档目的

本文档基于：

- 《Wonder Squad 游戏开发总设计文档 v1.1》
- 《Wonder Squad v1.1 设计变更影响分析》
- 原《Wonder Squad MVP 开发计划》

用于指导第一阶段 MVP 的范围、开发顺序与验收。

正式术语与依赖定义以 `Docs/01_Project/Project_Glossary.md` 为准。

MVP 的核心目标是验证：

> 2～4 名玩家进入一张独立小地图，通过不同角色能力、非语音或语音交流、环境解谜和创造不同方案完成冒险，并在欢乐失败和队友救援中持续游玩，是否足够有趣。

---

## 2. v1.1 计划原则

- 保留八个开发阶段，不增加独立的大型系统阶段。
- 非语音交流属于 MVP 必做项。
- 语音交流属于产品目标，但不进入第一阶段 MVP；MVP 只保留语音适配边界。
- 角色能力必须实际改变解法，但不能形成硬性阵容锁。
- 普通失败不重开整关，优先使用临时状态、队友救援和局部恢复。
- 一关一张独立小地图；第一版只制作《沉睡森林》。
- 不做随机大地图，只允许固定关卡内的有限变化。
- 玩家关卡编辑器不属于 MVP，只建设实际内容需要的数据驱动底层。
- 不为未来编辑器提前制作编辑器 UI、发布平台或通用脚本系统。
- 四个初始角色各实现一个标志性能力，允许重复角色。
- 关卡变体只建设数据支持，不进入第一阶段内容验收。

---

## 3. MVP 范围

### 3.1 必须实现

- 一张完整独立地图：《沉睡森林》
- 2～4 人联机合作
- 单局 10～20 分钟，目标约 15 分钟
- 基础移动、跳跃、镜头和互动
- 四个初始角色，各一个标志性 MVP 能力
- 每种角色能力至少一次有效关卡机会
- 缺少某个特定角色时仍可通关
- 世界与轻量小地图标记、快捷意图和必要角色动作
- 全队不开麦也能完成整关
- 资源采集
- 简单团队库存
- 道具拾取、携带、放置和使用
- 简单制作
- 三个合作机关
- 至少一个支持两种以上解法的主要障碍
- 至少一种搞笑临时状态
- 至少一种队友救援
- 普通失败后的局部恢复
- 玩家、角色、能力、标记、资源、道具、机关、失败状态、救援与关卡状态同步
- 数据驱动的关卡、机关、触发器和目标定义
- 关卡内变化的数据结构和校验边界，不要求实际随机启用

### 3.2 MVP 后续优先级

第一阶段 MVP 验证通过后再评估：

- 基础队伍语音 SDK。
- 实际启用关卡内随机变体。
- 更丰富的角色能力。

MVP 中只保留语音适配接口与关卡变体数据边界，不建立具体语音包依赖，也不要求变体进入完成标准。

### 3.3 明确不做

- 商城
- 氪金
- 排行榜
- 公会
- 连续开放大世界
- 随机生成大地图
- 复杂基地
- 大量角色
- 复杂战斗
- 复杂技能树与装备数值
- 玩家关卡编辑器 UI
- 玩家关卡发布、浏览、评分与审核
- 任意脚本式玩家触发器
- 自建独立后端
- 独立游戏服务器
- 完整账号与云存档
- 基础队伍语音 SDK
- 实际启用关卡随机变体

## 4. 核心体验与验证指标

### 4.0 交付优先级

- **P0 双人无麦窄切片：** 两个角色、一个能力差异、一个标记、一种资源、一个道具、一个多解法机关、一个临时状态和一次救援。
- **P1 完整 MVP：** 2～4 人、四个初始角色各一个能力、世界与小地图标记、三个机关及完整《沉睡森林》。
- **P2 MVP 后续：** 语音 SDK、实际关卡随机变体和更多能力。

P0 未验证核心体验前，不推进 P2。

### 4.1 核心循环

```text
组队与选择角色
→ 进入《沉睡森林》
→ 使用标记或语音表达意图
→ 探索并收集资源
→ 发现角色能力机会和环境问题
→ 选择能力、制作、地形或多人协作方案
→ 遭遇临时失败并互相救援
→ 完成三个机关
→ 修复传送门
→ 结算并返回关卡选择
```

### 4.2 强制验证指标

- 2、3、4 人均能稳定进入和完成同一局。
- 大多数有效测试局在 10～20 分钟内完成。
- 全队关闭语音时仍可理解目标、沟通和通关。
- 每种已实现角色能力在关卡中至少产生一次明确价值。
- 缺少任一特定角色的代表性阵容仍能完成主线。
- 至少一个主要障碍被测试者用两种以上方案完成。
- 普通失败不会要求重新加载整张地图。
- 至少发生一次玩家可理解的队友救援。
- 共享状态在所有客户端一致。
- 测试者能够描述合作、能力配合或创造方案带来的乐趣。

### 4.3 建议观察指标

- 有意义标记或快捷意图的使用次数。
- 玩家等待队友但无事可做的持续时间。
- 每种角色能力的使用率和贡献感。
- 角色优势解法与通用替代解法的完成时间差。
- 每种失败状态的平均持续时间。
- 队友救援成功率和放弃率。
- 三个机关的首次理解时间、重置次数和完成时间。
- 固定默认变体是否满足目标时长；实际随机变体评估延期到 P2。
- 测试后重玩意愿。

---

## 5. 内容与数据交付规范

MVP 不制作玩家编辑器，但所有关卡内容必须遵循：

- 关卡、角色、能力、道具、配方、机关、触发器和目标使用稳定标识。
- 静态定义与运行时状态分离。
- 《沉睡森林》不使用单个巨型脚本硬编码全部流程。
- 机关由有限状态、条件和动作组合。
- 每条主要解法描述能力、资源、人数和目标条件。
- 所有配置可校验缺失引用、非法组合和重复标识。
- 关卡变体只从白名单候选中选择。
- 内容格式包含版本号。
- 只实现当前三个机关实际需要的数据类型。

## 6. 开发阶段

## 阶段一：项目初始化

### 目标

建立统一、可联网验证、可数据驱动扩展的 Unity 项目基础，并冻结 MVP 边界。

### 具体任务

- 锁定 Unity `6000.3.21f1`（Unity 6.3 LTS）、Universal 3D、URP 和目标平台。
- 选定 Photon Fusion Host Mode 并完成最小连接验证。
- 记录语音适配边界，不安装或集成具体语音 SDK。
- 建立 Input System 输入图：
  - 移动与跳跃
  - 交互
  - 角色能力
  - 标记
  - 快捷动作轮盘
  - 救援
- 建立模块、程序集、目录和命名规范。
- 定义稳定 ID、配置版本和数据资产规则。
- 建立关卡、机关、触发器、条件、动作的最小数据模型草案。
- 创建 Bootstrap、Menu、SleepingForest 灰盒和专项测试场景。
- 建立基础日志、网络状态查看、内容校验和开发构建流程。
- 固定 P0、P1 和 P2 延期清单。

### 完成标准

- 所有人可用项目唯一正式版本 Unity `6000.3.21f1` 打开、运行并构建项目。
- 两个实例可创建并加入最小 Fusion 房间。
- 输入动作覆盖移动、能力、标记和救援。
- 至少一个数据定义可被加载并通过校验。
- 重复 ID 和缺失引用能产生明确错误。
- 已确认语音不进入第一阶段 MVP。
- 未开始编辑器 UI、后端或开放世界基础设施。

### 依赖关系

- 依赖 v1.1 设计文档和技术架构 v1.1。
- 是后续所有阶段的基础。

### 风险

- 数据驱动范围过大，演变为提前制作玩家编辑器。
- 网络或语音方案反复变更。
- 新输入过多导致手柄操作复杂。
- 为所有未来角色设计通用能力系统，延迟 MVP。

---

## 阶段二：单人移动和交互

### 目标

建立手感清晰的角色控制、统一交互、最小角色能力、非语音交流和救援原型。

### 具体任务

- 实现移动、转向、跳跃、跌落检测和受控 2.5D 摄像机。
- 实现通用目标发现、可用性查询、提示和交互请求。
- 实现拾取、携带、放下和放置占位物。
- 实现角色选择和最小能力执行接口。
- P0 为至少两种代表性能力做灰盒原型：
  - 环境移动/攀爬类
  - 环境激活/制作修饰类
- 实现场景标记：
  - 地点
  - 资源
  - 机关
  - 求助
- 实现快捷意图或动作轮盘最小集合：
  - 来这里
  - 等等
  - 我来
  - 需要帮助
  - 资源不足
  - 完成了
- 实现一种本地临时状态和一种救援交互原型。
- 实现检查点与跌落恢复。
- 建立键鼠和手柄操作测试场景。
- 为所有共享结果预留主机权威边界。

P1 扩展为四个初始角色各一个标志性能力：

- 探险家：预定义锚点移动或绳索路线。
- 工匠：预定义插槽修复或降低一次制作成本。
- 魔法师：切换预定义环境状态。
- 观察者：揭示预定义路线、资源或线索。

### 完成标准

- 单人可完成移动、交互、拾取、能力、标记和救援操作链。
- 标记可在一次或两次操作内发出并自动消失。
- 快捷动作不阻断角色控制过久。
- 临时状态能通过队友占位代理或调试工具解除，并有超时兜底。
- 摄像机不会频繁丢失角色或遮挡重要提示。
- 核心逻辑不依赖具体角色类名或场景对象名称。

### 依赖关系

- 依赖阶段一。
- 为资源、制作、机关、联机和完整关卡提供基础。

### 风险

- 能力与移动控制互相干扰。
- 标记和交互提示同时出现导致视觉噪声。
- 动作轮盘对手柄不友好。
- 临时状态让玩家长时间失去控制。

---

## 阶段三：资源采集

### 目标

建立服务于解谜、角色差异和替代路线的低摩擦资源系统。

### 具体任务

- 定义最小资源集合，例如木材、石块、水晶和零件。
- 实现数据驱动资源节点和候选生成点。
- 实现采集请求、反馈、耗尽和掉落。
- 使用轻量团队共享库存。
- 设计能力对采集的有限影响：
  - 更快发现
  - 更低消耗
  - 额外候选点
- 不让能力直接形成唯一资源入口。
- 定义角色优势路线和通用替代路线的资源预算。
- 设计单局内资源充足与恢复规则，不依赖重复刷新。
- 为主机权威、重复采集和候选点同步预留数据。

### 完成标准

- 至少三类资源可被发现、采集和加入团队库存。
- 两名玩家同时采集同一节点时结果唯一。
- 缺少能力角色时仍能得到主线所需资源。
- 替代解法资源成本更高但不需要重复刷取。
- 资源候选点由同一配置生成且能记录选择结果。
- 资源不足有可理解的非语音提示。

### 依赖关系

- 依赖阶段二的交互、能力和标记。
- 为制作和替代解法提供输入。

### 风险

- 共享库存削弱搬运分工。
- 能力效率差导致某角色成为必选。
- 候选资源点破坏关卡时长或可通关性。
- 资源种类过多增加认知成本。

---

## 阶段四：道具和制作

### 目标

让玩家利用资源和角色能力创造改变环境的工具，同时保留通用替代方案。

### 具体任务

- 定义少量配方与道具数据。
- 实现材料校验、原子消耗、制作结果和失败原因。
- 实现共同提交材料与团队制作。
- 实现场景道具的生成、拾取、携带、放置、使用和恢复。
- 设计能力对制作的有限修饰：
  - 降低材料成本
  - 替换一种材料
  - 解锁更快但非唯一的制作方式
- 为缺少工匠或其他能力设计通用配方。
- 实现关键道具离图、被丢失或持有者离开后的恢复。
- 记录不同解法使用的配方和道具标识。

### 完成标准

- 玩家可完成至少两种制作。
- 制作结果能改变环境或推进机关。
- 角色能力能提高效率，但无该能力仍有合理通用配方。
- 材料扣除是原子的，重复请求不会重复产出。
- 关键道具异常后不会永久卡关。
- 配方、道具和恢复点均由数据定义。

### 依赖关系

- 依赖阶段三的资源和库存。
- 依赖阶段二的能力与物体交互。
- 为三个机关提供工具。

### 风险

- 配方与角色能力组合过多。
- 通用配方成本失衡。
- 物理道具在联机下不稳定。
- 恢复机制可被玩家滥用复制物品。

---

## 阶段五：机关系统

### 目标

实现三个数据驱动的合作机关，验证角色优势、通用替代、非语音沟通和欢乐失败。

### 具体任务

- 实现有限的机关数据组件：
  - Trigger
  - Condition
  - Action
  - Puzzle State
  - Solution Path
  - Failure Output
  - Reset Rule
- 实现通用组件：
  - 按钮/压力板
  - 放置槽
  - 区域触发
  - 同步时间窗
  - 能量或路径连接
  - 状态施加与解除
- 灰盒实现三个机关：
  1. 沉睡藤门
  2. 回声石阵
  3. 古代传送门
- 每个机关定义：
  - 2 人基础解法
  - 3～4 人效率或并行机会
  - 至少一个角色优势
  - 缺少角色时的通用替代
  - 非语音提示与同步窗口
  - 失败状态、救援或局部重置
- 至少一个主要障碍支持两种以上实际解法。
- 为机关配置建立合法性校验和状态调试视图。

### 完成标准

- 三个机关都能从数据配置加载、完成和局部重置。
- 两人不用语音即可完成每个关键机关。
- 至少两个机关需要真实分工或同步。
- 缺少任何单一角色不会永久卡关。
- 至少一个机关失败会产生可继续的搞笑状态或支线情境。
- 机关非法状态可以恢复，不重载整张地图。
- 多条解法汇聚到唯一的权威完成状态。
- 配置缺失、非法条件和重复标识能被检测。

### 依赖关系

- 依赖阶段二至阶段四。
- 为完整关卡提供核心内容。

### 风险

- 数据组件过于通用。
- 多解法造成状态组合爆炸。
- 非语音同步窗口过严。
- 角色优势变成隐藏的角色硬锁。
- 失败状态与机关状态互相卡死。

---

## 阶段六：联机同步

### 目标

让 2～4 人稳定共享 v1.1 的全部核心状态，并确保所有关键结果由主机决定。

### 具体任务

- 实现创建、加入、离开、玩家生成和角色选择。
- 同步玩家输入、位置、动作和角色标识。
- 同步能力激活、持续时间和环境结果。
- 同步场景标记、快捷意图和求救状态。
- 对标记做类型、频率、位置、数量和生命周期校验。
- 同步资源、团队库存、道具和制作。
- 同步机关状态、解法结果、失败输出和局部重置。
- 同步临时状态、救援过程和解除结果。
- 支持主机种子与变体数据边界；MVP 使用固定默认变体。
- 处理玩家离开时的关键道具和受困状态。
- 对所有改变共享状态的请求做幂等处理。
- 测试延迟、抖动、丢包和两人同时操作。
- 语音只保留独立适配器接口，不接入具体 SDK。

### 完成标准

- 2、3、4 人均可进入同一《沉睡森林》会话。
- 所有玩家看到相同的角色、能力结果、标记、资源、道具、机关、状态和关卡阶段。
- 两人争用资源、道具或救援目标时结果唯一。
- 客户端不能直接宣布能力生效、救援成功或机关完成。
- 标记刷屏受限，本地隐藏不改变其他玩家状态。
- 玩家离开不会让关键道具或队友永久卡死。
- 固定默认变体在所有客户端一致。
- 完成多轮双人和四人联网核心链路测试。

### 依赖关系

- 依赖阶段一的网络方案。
- 依赖阶段二至阶段五可同步的玩法状态。
- 最小联网切片应提前进行，本阶段负责完整接入。

### 风险

- 新增共享状态导致同步边界混乱。
- 角色能力依赖非确定物理结果。
- 标记或动作事件占用过多带宽。
- 状态解除和玩家离开的先后顺序产生卡死。
- 语音 SDK 扩大平台与合规成本。

---

## 阶段七：完整关卡

### 目标

把所有系统组装为一局 10～20 分钟、全程可不开麦、任何合法阵容可通关的《沉睡森林》。

### 具体任务

- 完成独立关卡流程：
  - 进入与角色确认
  - 移动、标记和快捷意图教学
  - 森林探索与资源收集
  - 角色能力机会
  - 沉睡藤门
  - 回声石阵
  - 古代传送门
  - 完成反馈与结算
  - 返回关卡选择
- 为每个能力提供一次明显但非强制的价值。
- 为每个核心问题配置角色优势、通用替代和恢复解法。
- 布置资源、候选点、恢复点、支线和隐藏路线。
- 使用固定默认变体；实际随机变化延期到 P2。
- 加入至少一种搞笑状态和一种队友救援。
- 失败支线可提供笑点、资源或返回主线的机会。
- 用灯光、形状、图标、动作和短文本支持非语音理解。
- 确保重要信息不只依赖颜色或声音。
- 添加最小必要 UI、音效、动画和状态反馈。
- 记录人数、阵容、种子、解法、机关耗时、失败和救援。

### 完成标准

- 2～4 人从组队到结算完整通关。
- 大多数测试局在 10～20 分钟内完成。
- 全队关闭语音时仍能完成。
- 缺少任一特定角色的代表阵容仍可通关。
- 每种已实现能力至少有一次明显价值。
- 至少一个主要问题已用两种以上解法完成。
- 普通失败不重载整关。
- 至少一种状态需要并能够由队友救援。
- 三个机关均可局部恢复。
- 固定默认变体不破坏通关和时长。
- 不需要开发者现场干预。

### 依赖关系

- 依赖阶段二至阶段六。
- 为最终测试提供完整对象。

### 风险

- 新增体验挤压 10～20 分钟时长。
- 替代路线过长，形成对非最优阵容的惩罚。
- 提示过多削弱探索，过少又使无麦队伍卡关。
- 欢乐失败变成频繁打断。
- 为后续关卡变体过度建设会增加当前测试组合。

## 阶段八：测试和优化

### 目标

用外部玩家验证合作、角色能力、非语音交流、创造方案和欢乐失败是否好玩。

### 具体任务

- 建立人数矩阵：2 人、3 人、4 人。
- 建立代表性阵容矩阵：
  - 缺少探险家
  - 缺少工匠
  - 缺少魔法师
  - 缺少观察者
  - 两名相同角色
  - 四名相同角色
  - 2 人最不利能力覆盖组合
- 使用四角色可重复选择规则，对 2～4 人共 65 个无序组合执行结构通路校验；真实完整游玩使用上述代表性矩阵。
- 建立交流矩阵：
  - 全队不开麦
  - 部分玩家不开麦
- 建立失败矩阵：
  - 单人受困
  - 多人受困
  - 全队无法互救
  - 关键道具离图
  - 持有者离开
  - 机关非法状态
- 建立变体矩阵：
  - 默认资源点集合
  - 默认支线路线
  - 默认任务条件
- 进行内容配置校验；随机变体组合测试延期到 P2。
- 邀请未参与开发的玩家进行盲测。
- 记录沟通、能力、解法、失败、救援、等待和时长数据。
- 按阻断通关、破坏同步、损害核心体验、表现问题排序修复。
- 冻结功能，不在优化阶段加入玩家编辑器、后端或长期系统。

### 完成标准

- 不存在高频崩溃、严重不同步或稳定阻断通关问题。
- 2～4 人均完成多轮完整外部测试。
- 全队不开麦测试稳定完成。
- 代表性缺角阵容均有可接受的通关路径。
- 大多数有效测试局在 10～20 分钟。
- 普通失败平均恢复时间可接受，不导致大面积退出。
- 测试数据能回答五个问题：
  1. 合作是否有趣？
  2. 角色能力是否促进分工？
  3. 不开语音是否仍能顺畅合作？
  4. 玩家是否感到有不同解决办法？
  5. 失败与救援是否带来欢乐而非挫败？
- 形成继续开发、调整或重新验证的明确结论。

### 依赖关系

- 依赖阶段七完整版本。
- 小范围测试贯穿所有阶段。

### 风险

- 阵容和变体组合过多，测试失控。
- 熟悉项目的测试者掩盖无麦提示问题。
- 根据单个意见不断增加功能。
- 只修复错误，忽略角色无贡献或救援不好玩。

## 7. 阶段依赖与贯穿工作

主路径保持：

```text
项目初始化
→ 单人移动和交互
→ 资源采集
→ 道具和制作
→ 机关系统
→ 联机同步
→ 完整关卡
→ 测试和优化
```

贯穿主线：

- 网络可行性：阶段一开始，阶段六集中接入。
- 非语音交流：阶段二原型，阶段五用于机关，阶段六同步，阶段八无麦验证。
- 角色能力：阶段二建立，阶段三至五参与规则，阶段七整合，阶段八阵容验证。
- 欢乐失败：阶段二原型，阶段五作为机关输出，阶段六同步，阶段八恢复测试。
- 数据驱动：阶段一定义，阶段三至五使用，阶段七编排，阶段八校验。
- 范围控制：所有阶段维护“不做清单”。

## 8. 个人或 2～3 人团队推荐顺序

### 8.1 推荐开发顺序

1. 锁定 Unity、Fusion 和数据标识规则。
2. 完成单人移动、交互、一个角色能力和一个标记。
3. 完成一种资源、一个配方、一个道具和一个数据驱动机关。
4. 加入一种临时状态和一种救援。
5. 立即将这条窄切片接入双人联机。
6. 验证不开麦也能用标记完成窄切片。
7. 扩展到代表四种角色方向的最小能力集合。
8. 实现沉睡藤门、回声石阵和古代传送门。
9. 为三个机关补齐通用替代和恢复解法。
10. 组装《沉睡森林》完整灰盒。
11. 扩展至 3～4 人并验证固定默认变体的数据边界。
12. 完成无麦、缺角阵容和失败救援盲测。
13. 核心稳定并完成 MVP 验证后，再评估基础语音与实际关卡变体。
14. 冻结功能，修复阻断、同步和核心体验问题。

### 8.2 小团队分工

#### 程序方向

- 角色、能力、交互
- 资源、库存、道具、制作
- 机关、状态、救援
- 网络同步、数据校验和调试

#### 关卡与设计方向

- 三层解法
- 非语音提示
- 资源预算
- 关卡节奏
- 阵容和测试矩阵

#### 美术与综合方向

- 角色能力视觉语言
- 标记和动作
- 机关状态反馈
- 搞笑失败动画
- UI、音效和无障碍

两人团队可合并关卡与表现方向；所有成员都参与无麦联机测试。

### 8.3 里程碑

1. **基础操作版本**：移动、交互、能力、标记和恢复可用。
2. **单人数据闭环**：一种资源、配方、道具、机关、状态和救援。
3. **双人无麦闭环**：两人只用游戏内交流完成最小玩法链。
4. **三机关灰盒**：角色优势、通用替代和局部恢复成立。
5. **完整《沉睡森林》**：2～4 人在 10～20 分钟内完成。
6. **验证版本**：无麦、缺角阵容、救援和多解法通过外部测试。

## 9. MVP 完成定义

只有同时满足以下条件，MVP 才视为完成：

- 只包含一张完整独立地图《沉睡森林》。
- 支持 2～4 人完成联机冒险。
- 大多数有效测试局为 10～20 分钟。
- 非语音交流覆盖标记、快捷意图和求救。
- 全队不开麦可以通关。
- 少量角色能力具有清晰差异并参与解谜。
- 缺少任一特定角色不会永久卡关。
- 包含资源采集、简单制作和三个合作机关。
- 至少一个主要问题支持两种以上实际可用解法。
- 至少一种搞笑临时状态和一种队友救援可用。
- 普通失败不要求整关重开。
- 关键道具、机关和全队受困有恢复策略。
- 关卡、机关和触发器使用版本化、可校验的数据定义。
- 关卡变体数据边界通过结构校验；实际随机变体不属于 MVP 完成条件。
- 已通过外部玩家测试获得足以判断核心玩法是否好玩的证据。
- 未加入商城、氪金、排行榜、公会、开放大世界、复杂基地、大量角色、复杂战斗或玩家关卡编辑器。

## 10. v1.0 到 v1.1 版本变更记录

### 新增

- 非语音交流作为 MVP 必做项。
- 场景标记、快捷意图、角色动作和求救。
- 基础语音明确延期到 MVP 之后。
- 角色能力框架及其关卡验证。
- 角色优势、通用替代和恢复三层解法。
- 缺少特定角色的阵容测试矩阵。
- 搞笑临时状态、队友救援和全队脱困。
- 数据驱动关卡、机关、触发器、条件、动作和内容校验。
- 关卡内变体只保留数据边界，实际启用延期到 MVP 之后。
- 《沉睡森林》三个机关的 v1.1 设计方向。
- 全队不开麦、缺角阵容、失败救援和内容配置测试。

### 调整

- 核心验证目标从“合作、解谜、创造”扩展为“合作、角色能力、非语音沟通、创造方案和欢乐失败”。
- 关卡结构明确为一关一张小地图。
- 普通失败从快速重生表述调整为临时状态、救援和局部恢复优先。
- 资源、制作和机关增加角色能力与替代成本影响。
- 联机同步增加角色、能力、标记、临时状态、救援和随机种子。
- 完整关卡验收增加无麦通关和任意合法阵容可通关。
- 推荐开发顺序增加“双人无麦窄切片”。

### 删除或延期

- 删除随机生成大地图的方向。
- 玩家关卡编辑器、发布、浏览、评分和审核延期到 MVP 之后。
- 连续开放大世界继续排除。
- 语音不得替代游戏内交流，并已明确延期到 MVP 验证之后。
